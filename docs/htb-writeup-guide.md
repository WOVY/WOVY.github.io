# HTB 풀이 작성 가이드

Hack The Box 머신 풀이를 블로그에 기록할 때 쓰는 기준이다. 직접 쓸 때도, Claude Code·Codex 같은 AI에게 도움을 받을 때도 이 문서를 따른다.

## 왜 이렇게 쓰는가

1. **실무처럼 연습한다.** 본문 구조는 모의해킹 보고서(레드라쿤 양식)를 따른다. 요약 → 취약점 목차 → 수행 내용 → 취약점 상세 순서다.
2. **다른 풀이와 차별화한다.** 풀이 과정만 적지 않는다. 취약점마다 원인, 대응 방안, 조치 확인 방법, 탐지 포인트를 적고, 마지막에 배운 점을 남긴다.
3. **포트폴리오로 쓴다.** 글이 모이면 [`/writeups/`](https://wovy.github.io/writeups/) 페이지가 자동으로 표를 만든다. 이력서에는 이 링크를 넣는다.

## 작업 흐름

### 1. 풀기 전

- 머신이 **Retired**인지 확인한다. HTB는 Active 머신의 풀이 공개를 허용하지 않는다.
- Active 머신이면 블로그 CMS에 저장하지 않는다. 저장소가 공개라서 초안이라도 GitHub에서 원본이 보인다. 로컬 노트에 적어 두고 Retired된 뒤 옮긴다.

### 2. 푸는 중 (기록이 글의 재료다)

- 실행한 명령과 출력은 그대로 남긴다. 나중에 기억으로 재구성하지 않는다.
  - 예: `script -a htb-머신이름.log`로 터미널 전체를 기록하거나, nmap은 `-oN`으로 파일에 남긴다.
- 판단이 바뀐 순간을 메모한다. "왜 이걸 시도했는지", "왜 접었는지"가 나중에 가장 쓰기 어렵고, 가장 가치 있는 부분이다.
- 막혀서 힌트나 다른 풀이를 봤다면 어디를 봤는지 적어 둔다.
- 캡처는 판단 근거가 보이는 화면만 찍는다. 필요한 영역만 자른다.

### 3. root를 딴 뒤 (Beyond Root)

권한을 얻고 바로 끝내지 않는다. 대응 방안을 제대로 쓰려면 원인을 직접 봐야 한다.

- 취약했던 소스 코드나 설정 파일을 열어 문제 부분을 확인한다. (예: 웹 앱 소스의 파일 경로 처리, `/etc/sudoers`, cron 설정)
- 고치려면 어디를 바꿔야 하는지 생각해 본다. 가능하면 직접 고쳐 보고 같은 공격이 막히는지 확인한다.
- 공격 흔적이 어느 로그에 남았는지 본다. (예: `/var/log/nginx/access.log`, `/var/log/auth.log`)

### 4. 글 쓰기

1. 블로그 관리 화면(`/admin`) → **HTB 풀이** → 새 글.
2. 머신 정보 입력칸을 채운다. (아래 [머신 정보](#머신-정보-front-matter) 참고)
3. 본문 템플릿의 `[대괄호 안내문]`을 실제 내용으로 바꾼다. 쓰지 않는 절은 지운다.
4. 이미지는 CMS에서 올리면 `static/images/htb/`에 저장된다.
5. [공개 전 점검](#공개-전-점검)을 통과하면 "초안"을 끄고 저장한다. 저장하면 `main`에 바로 커밋되고 배포된다.

## 머신 정보 (front matter)

CMS에서 입력하면 글 파일 앞부분에 아래처럼 저장된다. 이 값으로 글 상단 정보 상자와 `/writeups/` 목록이 만들어지므로 본문에 다시 적지 않는다.

```toml
+++
title = "[HTB] Example"
date = "2026-11-22T20:00:00.000+09:00"
draft = true
summary = "LFI → 설정 파일 속 DB 비밀번호 → SSH 재사용 → sudo tar 와일드카드로 root"
tags = ["HTB", "Linux", "LFI", "sudo"]
post_template = "htb"

[htb]
machine = "Example"
url = "https://app.hackthebox.com/machines/Example"
os = "Linux"            # Linux / Windows / FreeBSD / OpenBSD / 기타
difficulty = "Easy"     # Easy / Medium / Hard / Insane
time = "6시간"
+++
```

| 항목 | 쓰는 법 |
| --- | --- |
| `title` | `[HTB] 머신이름` 형식으로 통일한다. (예: `[HTB] TwoMillion`) 기법은 제목에 넣지 않고 `summary`에 쓴다. |
| `summary` | 시작점부터 최고 권한까지 한 줄. 블로그 글 목록, 글 상단 정보 상자, `/writeups/` 표에 모두 나오므로 반드시 채운다. 화살표로 써도 되고 문장으로 써도 된다. |
| `tags` | `HTB`, OS, 핵심 기법·기술. 기존 태그와 표기를 맞춘다. |
| `post_template` | 반드시 `"htb"`. 이 값이 있어야 정보 상자와 목록에 나온다. CMS에서는 자동으로 들어간다. |

CMS 없이 직접 파일을 만들면 `content/posts/htb-머신이름.md`로 저장한다.

## 본문 섹션별 작성법

### 요약

2~3문장. 어디서 무엇을 찾아 들어갔고, 무엇 때문에 최고 권한까지 올라갔는지. 기술을 모르는 사람도 흐름을 알 수 있게 쓴다.

> 나쁜 예: nmap 돌리고 웹 들어가서 LFI 찾고 root 땄다.
>
> 좋은 예: 파일 다운로드 기능의 경로 조작으로 웹 설정 파일을 읽어 DB 비밀번호를 얻었다. 같은 비밀번호가 SSH 계정에도 쓰이고 있어 초기 접근에 성공했고, sudo로 허용된 백업 스크립트의 와일드카드를 악용해 root 권한을 얻었다.

### 발견한 취약점 (취약점 목차)

취약점마다 ID(`V-01`, `V-02` …)를 붙이고 표 한 줄로 요약한다. 본문의 수행 과정과 취약점 상세에서 같은 ID로 가리킨다.

위험도는 아래 기준으로 정하고, 근거는 취약점 상세의 CVSS 점수로 남긴다.

| 위험도 | CVSS 3.1 | 대략적인 기준 |
| --- | --- | --- |
| Critical | 9.0–10.0 | 인증 없이 원격에서 바로 시스템 장악 |
| High | 7.0–8.9 | 시스템 장악이나 중요 정보 유출로 바로 이어짐 |
| Medium | 4.0–6.9 | 다른 취약점과 묶이거나 조건이 있어야 피해가 큼 |
| Low | 0.1–3.9 | 단독으로는 피해가 작음 |
| Info | – | 취약점은 아니지만 공격에 도움이 된 정보 (버전 노출 등) |

CVSS 점수는 [FIRST CVSS 3.1 계산기](https://www.first.org/cvss/calculator/3.1)로 직접 매겨 본다. 점수를 매기는 과정 자체가 공부다.

### 수행 과정

단계 이름은 MITRE ATT&CK 전술 이름을 따른다.

| 절 | ATT&CK 전술 | 주로 쓰는 내용 |
| --- | --- | --- |
| 1. 정보 수집 | Reconnaissance | 포트·서비스 스캔, 디렉터리·서브도메인 탐색, 기술 스택 |
| 2. 초기 침투 | Initial Access | 첫 셸이나 첫 계정을 얻은 과정 |
| 3. 수평 이동 | Lateral Movement | 다른 사용자로 넘어간 과정 (없으면 절을 지움) |
| 4. 권한 상승 | Privilege Escalation | root·SYSTEM까지 올라간 과정 |
| 시도했지만 안 된 것 | – | 막다른 길과 접은 이유 |

#### 흐름 쓰는 법

공식 라이트업 여러 편에서 공통으로 보이는 서술 방식이다.

1. **행동마다 이유를 붙인다.** 문장마다 관찰 → 추론 → 행동을 잇는다. "디렉터리를 찾았다. 파일을 읽었다."처럼 행동만 나열하지 않고, "다운로드 링크가 파일명을 그대로 받는 것을 보고 경로 조작을 의심했다. 그래서 `../`를 넣어 요청했다."처럼 쓴다. 읽는 사람이 "왜 갑자기 이걸 하지?" 하고 멈추는 곳이 없어야 한다.
2. **지금 못 쓰는 단서는 보류로 남긴다.** 탐색을 마칠 때 "여기까지 알아낸 것" 목록으로 정리하고, 바로 못 쓰는 것은 `보류:`로 적는다. (예: "보류: SSH — 자격 증명이 생기면 시도") 나중에 그 단서를 쓸 때 "정보 수집에서 보류한 SSH에…"처럼 다시 짚는다.
3. **길을 낸 실패는 본문에 둔다.** 막힘 → 원인 추정 → 다음 시도가 있었다면 시도와 결과를 표로 남긴다. 성공한 명령만 있으면 운처럼 보이고, 과정이 있으면 실력으로 보인다. 끝까지 길이 안 열린 시도만 "시도했지만 안 된 것"으로 보낸다.
4. **위치가 바뀌면 확인한다.** 셸을 얻거나 사용자가 바뀔 때마다 `id`(Windows는 `whoami`) 출력을 붙이고 `현재 위치: 대상 호스트의 일반 사용자 user`처럼 적는다. 컨테이너 안인지, 어느 호스트인지도 적는다.
5. **소제목은 한 일로 짓는다.** 큰 단계(정보 수집, 초기 침투 …) 아래에 `#### HTTP`, `#### 다운로드 기능의 경로 조작`, `#### sudo 허용 스크립트의 와일드카드 악용`처럼 무엇을 했는지로 소제목을 단다. 소제목만 이어 읽어도 풀이 경로가 보이고, 목차가 그대로 요약이 된다.

#### 형식

- 명령과 요청은 코드 블록으로 그대로 붙인다. 출력은 판단에 쓴 줄만 남긴다.
- 코드 블록 언어는 `shell`(명령), `text`(출력), `http`(요청·응답), 소스는 해당 언어로 지정한다.
- 이미지는 판단 근거가 화면에만 있을 때 쓴다. 텍스트로 옮길 수 있으면 텍스트가 낫다(검색되고 복사된다).
- 이미지 alt 텍스트에는 화면에서 봐야 할 내용을 적는다. (예: `![업로드 후 응답에 저장 경로가 노출된 화면](/images/htb/example-upload.png)`)
- 단계마다 결정적인 생각을 `> 핵심 판단: …`으로 한 줄 남기면 읽는 사람이 흐름을 따라가기 쉽다.

"시도했지만 안 된 것"은 지우지 않는다. 실무에서도 시도한 것과 배제한 이유를 남기고, 면접에서 사고 과정을 보여 주는 데 가장 좋은 재료다. 다만 우회로 이어진 실패는 여기가 아니라 본문 흐름에 둔다.

### 취약점 상세

취약점 하나당 한 블록. 표의 각 항목은 이렇게 쓴다.

| 항목 | 쓰는 법 |
| --- | --- |
| 위험도 / CVSS 3.1 | 점수와 벡터 문자열을 같이 적는다. |
| 분류 | CWE 번호와 이름. 아래 자주 쓰는 CWE 참고. |
| 위치 | URL, 파라미터, 포트, 파일 경로처럼 바로 찾아갈 수 있게. |
| CVE | 공개된 CVE가 있을 때만. 없으면 행을 지운다. |

이어서 쓰는 항목:

- **원인** — 어떤 코드·설정이 문제인지. Beyond Root에서 본 소스나 설정을 인용한다.
- **재현 절차** — 다른 사람이 그대로 따라 할 수 있는 번호 목록.
- **영향** — 이 취약점 하나만으로 공격자가 할 수 있는 것. 연쇄 공격 결과까지 섞지 않는다.
- **대응 방안**
  - 즉시 조치: 오늘 당장 적용할 수 있는 완화책 (설정 변경, 기능 차단, 비밀번호 교체)
  - 근본 조치: 같은 문제가 다시 생기지 않게 하는 수정 (코드 구조, 권한 설계, 운영 절차)
  - 조치 확인: 수정 후 같은 공격을 했을 때 나와야 하는 결과. 이게 있어야 대응 방안이 검증 가능해진다.
- **탐지** — 이 공격이 어느 로그에 어떤 흔적을 남기는지. 관제·방어 쪽 관점이라 차별점이 크다.

대응 방안은 "입력값 검증 필요" 같은 일반론으로 끝내지 않는다. 이 머신의 이 코드·설정을 어떻게 바꾸는지 구체적으로 쓴다.

> 나쁜 예: 입력값 검증을 철저히 한다.
>
> 좋은 예: `download.php`가 `file` 파라미터를 경로에 그대로 붙이지 않고, 허용된 파일 ID 목록에서만 고르도록 바꾼다. 수정 후 `?file=../../etc/passwd` 요청은 400을 반환해야 한다.

### 배운 점

이 섹션이 공부의 핵심이다. 다른 사람 풀이를 베껴서는 채울 수 없다.

- **새로 알게 된 것** — 개념을 내 말로 설명한다. "X를 배웠다"가 아니라 "X는 이렇게 동작해서 이런 조건이면 악용된다"까지.
- **막혔던 지점** — 어디서 얼마나 막혔고 무엇을 보고 풀었는지. 힌트나 다른 풀이를 봤다면 정직하게 적는다.
- **다음 머신에서 바로 확인할 것** — 다음에 처음부터 점검할 항목. 글이 쌓이면 이 항목들을 모아 나만의 점검 체크리스트를 만든다.

### 참고 자료

공식 문서, CVE 설명, 참고한 글을 `[제목](URL) — 어디에 참고했는지` 형식으로 적는다. 다른 사람 풀이를 봤다면 여기에도 남긴다.

## 문체와 표기

모의해킹 보고서와 같은 문체로 쓴다. 글 자체가 보고서 작성 연습이 되고, 포트폴리오로 읽힐 때 기술 문서처럼 보인다.

- **서술은 "~한다"체.** 요약, 수행 과정, 배운 점처럼 흐름을 설명하는 부분. (예: 업로드 응답에 저장 경로가 그대로 노출됐다.)
- **항목은 개조식.** 취약점 상세의 영향, 대응 방안처럼 나열하는 부분은 "~함", "~음"이나 명사로 끝낸다. (예: 즉시 조치: 파일명 대신 허용 목록 ID로만 지정함)
- 한 글 안에서 "~습니다"체와 섞지 않는다.
- 솔직한 감상("이게 뭐지 싶었다")은 "~한다"체 안에서 그대로 둬도 좋다.
- 도구·명령·경로·파라미터는 `백틱`으로 감싼다.
- 용어는 처음 나올 때 한글과 영어를 같이 쓴다. (예: 경로 조작(Path Traversal))
- 대상 IP는 HTB에서 받은 그대로 써도 된다. 내 VPN IP는 `10.10.14.X`처럼 가린다.

## 공개 전 점검

- [ ] 머신이 Retired 상태다.
- [ ] `[대괄호 안내문]`과 `<!-- 주석 -->`이 남아 있지 않다. (주석은 화면에 안 보이지만 저장소 원본에는 남는다)
- [ ] 플래그(`user.txt`, `root.txt`), 비밀번호 해시는 가렸다.
- [ ] 내 VPN IP, 계정 이름 등 개인 정보가 캡처에 없다.
- [ ] 발견한 취약점 표의 ID와 취약점 상세의 ID가 맞다.
- [ ] 모든 취약점에 대응 방안과 조치 확인이 있다.
- [ ] 머신 정보의 요약(`summary`)이 본문 "요약" 절과 맞다.
- [ ] 이미지가 모두 보인다. (CMS 미리보기 또는 `hugo server`로 확인)

## AI가 도울 때 지킬 것

이 블로그 주인은 공부가 목적이다. AI는 대신 풀어 주거나 대신 써 주는 역할이 아니라, 기록을 정리하고 빈 곳을 짚어 주는 역할을 한다.

- **없는 결과를 만들지 않는다.** 명령 출력, 응답, 파일 내용, 플래그는 사용자가 준 것만 쓴다. 필요하면 "이 단계의 출력을 붙여 달라"고 요청한다. 추측으로 채운 부분은 `[확인 필요]`로 표시한다.
- **배운 점은 대신 쓰지 않는다.** 대신 질문으로 끌어낸다. (예: "sudo 규칙에서 무엇이 문제였다고 생각해요?", "다음 머신에서는 뭘 먼저 확인할 거예요?") 사용자가 답한 내용을 다듬는 것은 괜찮다.
- **원인과 대응 방안은 근거를 같이 준다.** 공식 문서, CWE, 벤더 권고를 링크한다. 일반론 대신 이 머신의 코드·설정 기준으로 쓴다.
- **위험도와 CVSS는 계산 근거를 보여 준다.** 벡터의 각 값(AV, AC, PR …)을 왜 그렇게 골랐는지 한 줄씩 설명해서 사용자가 판단을 따라가게 한다.
- **Active 머신이면 블로그 저장소에 쓰지 않는다.** 머신 상태가 불분명하면 먼저 묻는다.
- **문체 기준을 지킨다.** [문체와 표기](#문체와-표기)대로 서술은 "~한다"체, 항목은 개조식으로 쓴다. 사용자의 솔직한 표현은 매끈한 문장으로 지우지 않는다.
- **답변은 한국어로 한다.**

### AI에게 요청하는 예

- "이 nmap 결과랑 메모로 '정보 수집' 절 초안 잡아 줘. 판단은 내가 쓸게."
- "V-01 대응 방안이 너무 일반론인지 봐 줘."
- "이 취약점 CVSS 벡터 같이 매겨 보자. 값마다 이유 설명해 줘."
- "공개 전 점검 돌려 줘."
